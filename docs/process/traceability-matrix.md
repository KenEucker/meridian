Idempotency rests on `uuid`: a redelivery resolves to the stored operation before any acceptance check re-runs, is neither stored nor applied twice, and a concurrent duplicate insert resolves to the winner through the unique index; the same `uuid` with different content is refused as a replay. Refusal and failure stay distinct — a malformed envelope, an operation addressed to another node, an unknown or revoked origin node, an unknown acting user, an unknown or revoked acting device, and a signature that does not verify are refused without ever being stored and are audited as `node_operation.rejected` with a stable reason code, while an accepted operation that cannot be applied is stored and marked `failed` with a `failure_reason` and incremented `retry_count` so it stays recoverable and does not block unrelated sync. Nothing is applied from `payload_json`: signatures cover the normalized fields only, so the payload is unauthenticated and changeable in transit, and appliers are handed the `SignedNodeOperation` projection with no access to it. The payload is still stored for conflict review but is non-authoritative, which means an operation's meaning must live in `operation_type` and the entity it names rather than in payload data. Per-entity appliers, the bidirectional sync loop (M12.5), event authority enforcement (M12.6, M12.7), and the conflict queue/resolver (M12.8, M12.9) remain with their owning tasks; M12.4 decides only that an operation is well formed, addressed here, authentic, and from a node and device this install still accepts. M12.5 closes the loop with the sending half and the transport. `NodeOperationRecorder` creates an operation on this node, signs it before insert, and stores it `pending`, which is the queue on-site holds operations in while there is no internet; `NodeSyncOutbox` decides what is still owed to a peer, offering only operations that originated here so two nodes cannot bounce the same operation back and forth, oldest first so ordered entities arrive in origin order, and bounded by a batch size. `POST /api/node-sync` is one exchange in both directions: the caller pushes its queued operations in the request and this node's queued operations come back in the response, which is what makes sync bidirectional rather than push-only without central having to reach into an event network. The exchange is signed by the calling node over `meridian.node-sync.v1` plus the source node, `sent_at`, and the operation/acknowledgement/refusal uuid lists, and verified against the peer public key registered at pairing; operation contents are not covered because each operation is separately node-signed. Exchange authentication exists because the response hands operations back, so an unauthenticated caller could otherwise pull this node's queue. An exchange from an unknown, revoked, or never-paired node, one outside a two-sided clock window that bounds replay, and one whose signature does not verify are refused with a stable reason code and audited as `node_sync.refused`, and nothing is returned. Delivery state is confirmation-based: `pending` becomes `sent` only when the peer says it holds the operation, because a response lost in flight would otherwise drop an operation nobody would resend, while redelivery is safe on `uuid`. An operation the peer refuses becomes `failed` with the peer's reason so it leaves the queue instead of being offered forever, and a peer can only settle operations that originated on the receiving node. One refused operation is reported and the rest of the batch continues (technical spec 10.3). A run is a loop of exchanges that carries the previous exchange's acknowledgements and refusals forward, so a backlog drains within a run and no ack bookkeeping is persisted between runs; an interrupted run just gets the operations re-offered and stores them idempotently. `meridian:node-sync` runs the loop and is scheduled every minute, exiting successfully on an unreachable peer because a queued on-site node is the designed behavior, and failing when the node is unpaired, cannot sign, or is refused. Event authority during an active event window (M12.6, M12.7), the conflict queue and resolver (M12.8, M12.9), and Electron sync health (M12.10) remain with their owning tasks; per-entity operation vocabularies and appliers stay with the tasks that own each entity's sync. M12.5 also adds the God-mode read of that state: `NodeSyncHealth` derives sync health from the operation log and the refusal audit trail rather than storing a run status, because a stored status would let a run that died mid-way look healthier than one that finished and reported a problem. The node configuration screen shows queued/delivered/refused in the sending direction and received/applied/unapplied in the receiving direction — counted apart because undelivered means this node cannot reach its peer while unapplied means the peer was reached and something local is wrong — plus the oldest queued operation, last send, last receipt, recent operation failures, and recent refused exchanges, which have no operation row and exist only in audit. Queued work is reported without alarm because a backlog during an outage is the designed behavior; only failures and refusals set the attention state. Electron health (M12.10) surfaces the same signals on-site. |
