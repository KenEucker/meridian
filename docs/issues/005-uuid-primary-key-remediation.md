# 005: Canonical UUID Primary Key Remediation

## Type

Technical foundation / change control (spec-alignment remediation)

## Traceability

- Data/API spec: Section 4.1 Canonical IDs
- Data/API spec: Section 4.3 Human-Facing Numbers
- Technical spec: Section 6.2 IDs
- Technical spec: Section 10 Node sync (collision-free identity is a prerequisite)

## Summary

Align the implemented database schema with the governing identifier policy. Data/API spec section 4.1 and technical spec section 6.2 require that **all externally referenced canonical records use UUID primary keys** (and UUID foreign keys, API references, sync identity, audit references, and authorization identifiers).

Several Alpha 1 tables were implemented with Laravel's default auto-increment `bigint` primary keys instead of UUIDs. This remediation converts those tables, and their foreign-key references, to UUIDs.

## Background: how the deviation happened

The UUID identifier policy was applied inconsistently across milestones:

- Tasks that dealt with device/offline/sync-originated or event records applied UUIDs (e.g. the events task PR explicitly cited "Sections 4.1-4.3 UUID identifier policy").
- Tasks that dealt with central/admin records used the framework default `$table->id()` and did not cite section 4.

There is no architecture decision record or technology-baseline entry authorizing `bigint` primary keys, so this is unflagged implementation drift, not an accepted decision. The specs continue to govern.

## Why this matters

This is not cosmetic. Central/on-site node sync (Milestone 12) depends on globally unique, collision-free identity:

- Auto-increment `bigint` keys are generated independently per node, so central and on-site nodes can mint the same integer id for different records.
- Section 4.1 explicitly requires UUIDs for sync identity and audit references, and section 4.1/6.2 require that "UUIDs may be generated by the creating node or trusted device before sync" and that "central preserves original on-site/device UUIDs forever."

The conversion should land **before Milestone 12 (node sync)** because converting primary key types after sync and operation history exist is significantly harder.

## Remediation approach: no data to preserve

The platform is still in active development and there is **no pre-existing data to retain** (the database is empty and is rebuilt from migrations).

Because of this, the remediation does **not** use data-preserving conversion migrations or backfills. Instead:

- Edit the original table-creation migrations in place so each affected table uses `$table->uuid('id')->primary()` (and `HasUuids` on the corresponding model with `$incrementing = false` / `$keyType = 'string'`).
- Update every referencing foreign-key column to `foreignUuid(...)` (or `uuid(...)` for deferred/nullable placeholder references) so the column type matches the new key type.
- Rebuild the development database with `php artisan migrate:fresh` (and `--seed` where seeders apply).
- Do **not** add ALTER/backfill migrations; do **not** add production data-migration safety steps. These are unnecessary while there is no data.

If real data ever exists before this lands, this approach must be revisited.

## Scope

In scope:

- Convert the `bigint`-keyed canonical tables listed above to UUID primary keys by editing their creation migrations and models in place.
- Update all foreign-key columns that reference those tables (across all migrations) to `foreignUuid` / `uuid`.
- Convert `audit_events` foreign-key columns (`organization_id`, `department_id`, `actor_user_id`, `actor_node_id`) and the polymorphic `entity_id` column to UUID once the referenced tables are UUID.
- Update factories, seeders, and tests that assume integer ids.
- Rebuild the dev database with `migrate:fresh`.

Out of scope:

- Human-facing numbers (incident numbers, FRA numbers); these remain separate from UUIDs per section 4.3 and must never be used as primary or foreign keys.
- Any new product behavior.

## Acceptance criteria

- Every canonical table listed above uses a UUID primary key.
- Every foreign key that references a converted table uses a matching UUID column type, and migrations run cleanly with `php artisan migrate:fresh`.
- `audit_events` foreign-key columns and `entity_id` are UUID; the `AuditService`/`AuditEvent` write path records UUID entity references.
- No auto-increment `bigint` primary key remains on a canonical, externally referenced table.
- Human-facing numbers are unaffected.
- Factories, seeders, and the full server test suite pass.

## Automated tests

- `php artisan migrate:fresh` (and `--seed`)
- `php artisan test`
- `scripts/process/check.sh`

## Notes

This issue exists because M4.9 (audit service baseline) surfaced the deviation while choosing a key type for `audit_events.entity_id`. M4.9 ships its own primary key as a UUID immediately; the remaining foreign-key/`entity_id` conversion is folded into this remediation so the audit table reaches full section-4.1 compliance alongside the tables it references.
